# Transport, audio, input, and ownership

`SwiftlightTransport` wraps the C `CStreamBridge` target. The only media transport is the pinned Moonlight common-c Git submodule with targeted patches; there is no alternate video decoder in either target. `StreamTransport` is single-use and common-c permits only one active session per process. Swift serializes `LiStartConnection` and `LiStopConnection` on a lifecycle queue. Cancellation uses only `LiInterruptConnection` while start is pending and joins start before stop. Bridge state uses explicit acquire/release atomics because the input and callback gates serve different lifetimes; neither gate is acquired while holding the other. C input APIs hold an admission mutex while using common-c, so disconnect closes admission before common-c tears down its input queue. Held keyboard, mouse and controller buttons are released before stop. Disconnect never invokes host `/cancel` or `/quit`.

## Compressed frame ownership

For an explicit HEVC/AV1 4:4:4 request, connection preparation intersects separate host and device 8-bit/10-bit profile capabilities before launch. Server codec-mode bits (`0x00080000`/`0x00100000` for HEVC, `0x00200000`/`0x00400000` for AV1) are distinct from negotiated video-format bits (`0x400`/`0x800` and `0x4000`/`0x8000`). Transport advertises only the selected profile. The setup callback carries its exact chroma and depth into the native decoder, whose output must preserve that sampling. The existing common-c implementation already negotiates these formats; generated sources and upstream pins are unchanged.

The renderer advertises `CAPABILITY_PULL_RENDERER` without direct-submit or reference-frame-invalidation capabilities. A dedicated pthread calls `LiWaitForNextVideoFrame`, validates and flattens the complete access unit including HEVC parameter sets, and calls the Swift admission closure synchronously. No video decoding occurs on a receive thread. The closure returns success only after the selected native decoder has acquired the compressed bytes; then `LiCompleteVideoFrame(handle, DR_OK)` relinquishes the common-c frame. Rejection, malformed input, cancellation and overflow converge on exactly one `LiCompleteVideoFrame(handle, DR_NEED_IDR)`.

The flattener has a 32 MiB reusable buffer, a 65,536-entry validation bound and one AU undergoing decoder admission. It holds one borrowed C frame handle, or briefly two while polling a replacement before completing the older PyroWave handle. Swift acquires a value-owned Data copy before invoking the decoder callback. MoonlightAppleVideo's HEVC/AV1 submit-copy acquires its own bytes; the direct PyroWave bridge passes bounded intact ranges to the pinned native parser and completes its compressed upload before returning. These explicit copies are the correctness baseline and have not been promoted as an optimization. No borrowed C pointer escapes. The app closes decoder admission, waits for the transport worker to join, then drains/destroys the decoder. Capacity waits belong in the decoder adapter and retain the same compressed AU; obsolete decoded presentation frames may be replaced, compressed reference frames may not be arbitrarily dropped.

Explicit PyroWave streams use the same RTP, encryption, FEC and pull-worker ownership path. The fifth common-c patch negotiates the four PyroWave profiles with `bitStreamFormat=3`, record-framing features, and the matching chroma/bit-depth masks. An explicit incompatible advertised bitstream revision fails the RTSP handshake; a legacy host without the advertisement remains permitted with compatibility unverified. An unavailable selected profile fails instead of falling back to another profile or codec. PyroWave payloads bypass NAL processing and retain exact last-payload trimming. Frames are independent and the explicit keyframe-request API is a no-op for this codec.

After setup selects PyroWave, the pull worker selects the newest queued AU before decoder admission, with at most 15 polls per selection so continuous reception cannot starve admission. Each replaced handle completes exactly once with `DR_OK` and increments `compressedStaleSkips`; it remains an acquired AU and does not increment network loss. The selected AU retains its own sequence header, timestamps, HDR metadata and fragment sideband. The direct bridge clears native PyroWave state before submitting each frame, including the first; codec acceptance and decode readiness use the pinned decoder's native API. This selection also applies to queued partial PyroWave AUs; the bridge preserves bounded intact ranges and loss boundaries, while useful partial decoding remains the decoder's responsibility. Already admitted work keeps its terminal completion. HEVC and AV1 retain FIFO admission even when PyroWave was among the offered formats. Queue selection, PyroWave sideband interpretation and keyframe suppression use the successfully negotiated format.

After FEC recovery, an incomplete PyroWave block can be delivered with zero-filled lost data packets when the next block or frame arrives. Missing first packets and entirely missing FEC blocks still drop that frame. `CompressedVideoFrame.pyrowaveFragments` retains every RTP payload boundary, including normal, lost and record-start buffers, and `pyrowaveCriticalPackets` carries the host's required coarse-data prefix. Both arrays and flattened compressed bytes become value-owned before the borrowed callback returns. Record parsing and partial-decode acceptance remain in the pinned native PyroWave parser, reached through `CPyrowaveBridge`. Confirmed network-loss counters include partial frames with unrepaired packet loss, even if their remaining records are useful to the decoder; complete-reassembly counters exclude them.

All codecs capture `hdrActive` and optional `TransportHDRMetadata` from the control channel when the decode unit is assembled. A scoped common-c publication gate captures active state and metadata together; the bridge copies these values with the AU before invoking Swift. HEVC and AV1 use only the mastering-display and content-light values as per-AU fallbacks for missing bitstream or CoreVideo metadata; host HDR state does not override their decoded transfer function, primaries, range or chroma location. PyroWave also uses the captured HDR state to describe its GPU planes. Chromaticities retain their 1/50000 units, minimum luminance its 1/10000-nit units, and other luminance/light values their nit units. Optional host values remain zero. The same synchronization protects the official HDR getters and async event reader. No event-delivery ordering is used to color a queued AU. HDR control messages have no frame ID, so dynamic transitions still expose the latest reported state at assembly rather than a verified encoder-to-frame association.

The PyroWave SDR fallback requests Rec.709 in `encoderCscMode`, including 10-bit profiles. [Vibepollo's color selection](https://github.com/Nonary/Vibepollo/blob/master/src/video_colorspace.cpp) overrides that request with BT.2020 PQ when the host display and request actually enable HDR; otherwise it follows the requested SDR matrix. Requesting Rec.2020 merely because the profile is 10-bit would instead yield BT.2020 SDR on an SDR host, whose transfer differs from PQ.

The production `consume_frame` owner is the same code used by the deterministic native and Swift tests. Six cases cover successful acquisition, decoder rejection, inconsistent length, cancellation after acquisition, oversize input and a cyclic fragment chain. Every acquired handle completes once; rejected malformed input never reaches the decoder closure.

Ten native queue-selection cases cover a single AU, a queued burst, continuous replenishment beyond the poll bound, HEVC/AV1 FIFO admission, cancellation before and during selection, decoder rejection after local replacement, and mixed offered masks that negotiate HEVC or AV1. They verify exact-once handle completion, local skip accounting, selected-AU identity and sequence-header preservation, and codec-scoped sideband interpretation.

## Clock domains and route evidence

common-c's Darwin `PltGetMicroseconds` is `(CLOCK_UPTIME_RAW - start_ns) / 1000`. MoonlightAppleVideo's `mav_monotonic_time_ns` is absolute `CLOCK_UPTIME_RAW` nanoseconds. A minimal patched accessor returns immutable `start_ns`; the bridge adds it to receive/enqueue microseconds to expose `receiveUptimeNanoseconds` and `enqueueUptimeNanoseconds`. The conversion has less than one microsecond of floor quantization. RTP presentation timestamps remain in a separate 90 kHz/first-capture domain and must not be subtracted from the uptime clock.

Each decode unit also retains transport milestones from that same frame. `lastRequiredPacketReceiveTimeUs` samples entry to the userspace RTP queue for the accepted packet that makes the final FEC block recoverable, including parity when recovery is needed. It excludes kernel arrival, socket delivery and decryption before the queue entrypoint; the first-packet clock now samples that same entrypoint. Duplicates, reconstructed packets and synthetic lost packets never advance it. It is unavailable for any partial frame because missing packets never arrived. `fecReadyTimeUs` samples completion of final-block reconstruction or loss synthesis and ordering, immediately before whole-frame depacketization. For multi-block frames, all packet entries carry the same final-frame milestones, so early completed blocks cannot be mistaken for frame readiness.

The existing `enqueueTimeUs` remains decode-unit creation after depacketization. `queueOfferTimeUs` is sampled immediately before the actual blocking-queue offer or direct-submit callback, after HDR snapshot and keyframe bookkeeping. The C bridge additionally records `transport_handoff_uptime_ns` immediately before the synchronous Swift callback, after AU validation and flattening. All absolute bridge milestones use the same uptime conversion; zero is unavailable. `payload_bytes` is the exact depacketized AU length, excluding transport headers/parity. Partial frames include zero-filled missing payload placeholders and carry `transport_partial`, so this value is not wire throughput or intact received bytes. The measurements separate packet availability, final FEC/order work, depacketization, queue publication and pull-worker handoff; the receipt span still combines host packet pacing, network delivery, receiver scheduling and earlier-block FEC/order work performed before later packets enter the single receiver. Last-required to final readiness isolates work after the final decisive packet, not cumulative FEC CPU time for all blocks.

`StreamTransport.diagnostics` reads common-c RTT and variance, pending video/audio, and local audio queue counters. A minimal `VideoStream.c` accessor uses `getsockname` on the actual bound video UDP socket. The address is matched against `getifaddrs` to identify its interface. This does not infer an existing media socket's route from a global `NWPathMonitor`. The fourth targeted patch exposes complete RTP frame and confirmed network-loss counters. Host processing and reassembly summaries use bounded recent windows; frame-arrival variation is separately labeled. See [stream statistics](stream-statistics-implementation.md) for exact units, exclusions and offline evidence. Unmeasured Wi-Fi signal strength, wire throughput and one-way latency remain unavailable.

## Audio

The selected Stereo, 5.1 Surround or 7.1 Surround setting drives both the host launch/resume request and common-c audio configuration. Stereo and Direct remain the defaults. The Opus multistream mapping supplied by common-c is passed unchanged to the pinned libopus decoder. common-c defines its output order as front left, front right, center, LFE, back left, back right, side left, side right; stereo and 5.1 use the first two and six channels respectively. Apple output formats explicitly describe the corresponding channel layout. Physical headphone channel count does not prevent a surround request.

common-c retains its packet loss/jitter queue and calls Opus decoding on its audio decoder worker, never on the Core Audio callback. Missing packets use Opus PLC. Both output modes consume native interleaved Float32 PCM from this decoder. Direct uses the default-output Audio Unit on macOS (RemoteIO conditional scaffolding for future Apple platforms). Its lock-free single-producer/single-consumer ring holds at most 2,048 sample frames (42.67 ms at 48 kHz), independent of channel count. Atomic acquire/release indices protect occupied cells. The producer rejects a whole arriving decoded packet on overflow; it never overwrites unread storage or advances the consumer index. The Audio Unit callback copies available samples and emits silence on underrun, with no allocation, locks, network calls or Opus work. Overflow and underrun sample frames are counted. The queue size is an initial bounded policy, not a measured optimum.

System Spatial Audio uses `AVSampleBufferAudioRenderer` attached to an `AVSampleBufferRenderSynchronizer` before playback. Correctly described multichannel PCM is timestamped on the audio sample timeline and the renderer's `allowedAudioSpatializationFormats` is `.multichannel`. It consumes the same bounded PCM ring in 960-frame batches (20 ms at 48 kHz). Preroll is collected while paused; its route floor sums public Core Audio device latency, stream latency, safety offset and buffer frames, converts them to 48 kHz and rounds to whole batches with an 80 ms minimum. Playback starts at that floor; Apple's sufficient-media signal is diagnostic-only. The running target is the accepted preroll plus one batch, capped at 480 ms; a whole batch can extend submitted PCM to the 500 ms cap. Together with the 42.67 ms ring, the maximum software bound is 542.67 ms, excluding system/device latency. The earlier AirPods route floor of 180 ms and running target of 200 ms are buffering estimates, not measured end-to-end latency. Preroll begins with real PCM, then may pad input gaps at realtime pace; running gaps are padded while leaving one batch interval for collection. Missing frames count as ring underruns.

Stereo is independently gated to Direct in settings and transport so a saved stereo/spatial combination cannot add another spatial effect to a host headphone mix. Apple's renderer controls physical output and eligible spatialization; selecting this backend is not proof that Spatial Audio, Head Tracked or Personalized Spatial Audio is active. It does not replace the Metal video renderer, introduce AVPlayer, request head-pose/profile entitlements or implement a custom virtual-speaker engine.

Direct output observes macOS output-device, nominal-sample-rate, stream-layout and device-alive properties on a dedicated serial control queue. Route changes discard stale PCM and rebuild direct output while retaining Opus history. System output coalesces AVFoundation automatic-flush and output-configuration notifications, requests a normal pause that preserves its synchronizer epoch, and waits for both effective rates to acknowledge the pause. It then flushes submitted audio, drops old ring PCM, and collects new preroll at the stopped playhead. Resume requires both the route-derived preroll floor and effective-rate acknowledgment. Actual unplayed sample-buffer intervals determine submitted-frame counts. A host-monotonic stale-input watchdog discards ring data without rebuilding the graph.

A bounded recovery timeout or renderer failure permits one audio renderer/synchronizer replacement per stream. Generation checks reject callbacks from retired renderers. The replacement does not reconnect video or recreate the host stream. A second unrecovered failure emits an explicit audio error; it does not enter an indefinite replacement loop or substitute another backend. The rewritten native offline suite, all six real-output smoke paths with running-state assertions, and an independent forced replacement/teardown harness passed under AddressSanitizer/UndefinedBehaviorSanitizer. The integrated Swift suite passed 102 tests after the rewrite.

Direct downmixes locally when the selected output has fewer physical speaker channels. Source negotiation remains unchanged across routes. Removal of listeners and draining the control queue precede context destruction. Application sleep/suspension uses the app session lifecycle. The user confirmed audible 7.1 Direct and System Spatial Audio on AirPods, including recovery that stayed audible after repeated Fixed/Off/Head Tracked changes on the signed final build. Logs showed 180 ms preroll, a 200 ms running target, active effective rates and advancing real PCM; observed mode changes recovered within the same renderer generation. Channel isolation, head-pose quality, other devices, physical latency and 30-minute drift testing remain pending. The mobile adapter configures AVAudioSession and disconnects locally on interruption or an incompatible route change; physical iPhone/iPad audio acceptance remains separate. tvOS audio-session integration is future work. See [audio settings and physical acceptance](audio-implementation.md).

## Input and Apollo permissions

Input is forwarded independently of decoder backpressure. Keyboard VK values are normalized to the GameStream `0x8000 | VK` representation before enqueueing; the same normalized key is stored and used for held-key release. Stream configuration takes optional authenticated Apollo `Permission` bits. A missing field means a standard host; explicit zero denies all input. Controller (`0x100`), native touch (`0x200`), mouse (`0x800`) and keyboard (`0x1000`) paths are gated in C before enqueueing. These constants are verified against [Apollo `src/crypto.h`](https://github.com/ClassicOldSong/Apollo/blob/adc5c5a0bd80831ce495434bb16aee2cd4175fb8/src/crypto.h) at `adc5c5a0bd80831ce495434bb16aee2cd4175fb8`; native touch has its own grant and does not borrow the mouse or pen grant. No pen path is advertised. The macOS app owns keyboard mapping, capture and GameController hot-plug/haptics. Core transport keeps held-state release bookkeeping.

`StreamTransport.nativeTouchAvailability` checks the active stream, authenticated touch permission and negotiated `LI_FF_PEN_TOUCH_EVENTS` feature under the C input-admission mutex. It distinguishes supported, unsupported, denied and not streaming. `touch(event:id:x:y:pressure:)` forwards explicit down/move/up/cancel phases through common-c's `LiSendTouchEvent`, validating finite coordinates and pressure within 0...1. Pressure 0 means unknown; contact area is unknown (0) and rotation uses `LI_ROT_UNKNOWN`. Only successfully enqueued down events own one of 16 bounded native contact slots. Duplicate down and stale move/up/cancel are rejected. A failed terminal enqueue keeps ownership for subsequent cleanup. Previously accepted contacts may cancel after a permission/capability change, without sending new motion data. `releaseAllInputs` sends `CANCEL_ALL` for owned contacts before stop closes common-c admission and retires their local IDs even if the cancellation enqueue fails. Platform input adapters decide when to use native touch or mouse behavior; this shared bridge does not create UI or establish physical touch/host interoperability.

- Opus 1.5.2, SHA256 `65c1d2f78b9f2fb20082c38cbe47c951ad5839345876e46941612ee87f9a7ce1`.
- OpenSSL 3.6.4, SHA256 `9bffaa1ad1e07b354c21bd3324ec02fa15579f45a7d0494b3e74bc449b7333ef`.

`Connection.c` has a scoped lifetime patch: the termination callback thread remains joinable and is joined after media/control threads and before platform cleanup. Upstream detaches it, which could let late termination delivery observe a new process-global session. The internal cancellation flag is atomic, and termination notification uses an atomic exchange so concurrent failures cannot create two competing callback threads. The matching internal declaration is in `Limelight-internal.h`. Swiftlight event callbacks enqueue orchestration and must never call stop inline. Two additional read-only accessors expose the common-c clock epoch and bound video socket address. The original three patches apply to both the audited Qt reference `874ac954` and selected upstream `62e0663`. A fourth patch, developed against `62e0663`, records complete and irrecoverable RTP frame outcomes using per-queue atomics and a gated read-only accessor. A fifth ports the PyroWave protocol from Nonary's common-c revision `927eba9`, adapting it to retain the selected upstream's newer recovery fixes and the existing counters. A sixth adds per-frame transport milestones without changing queue admission or FEC/recovery policy. All six are separately reviewable under `patches/moonlight-common-c`; the standalone native validator prepares and verifies the generated tree before compiling.

## Reproduce offline validation

```sh
scripts/bootstrap-dependencies.sh
CLANG_MODULE_CACHE_PATH="$PWD/.build/ModuleCache" swift test --disable-sandbox --filter TransportTests
scripts/validate-transport-native.sh
SWIFTLIGHT_SANITIZERS=thread scripts/validate-transport-native.sh
```

The native command compiles owned code and the generated upstream transport with AddressSanitizer/UndefinedBehaviorSanitizer by default. It exercises exact frame completion and stereo ring wrap, overflow, silence, route-discard and 100,000 concurrently transferred ordered frames. It also validates exact clock mapping, Apollo input gates, a deliberately blocked callback racing context retirement, and 1,000 repeated callback-context retirements. It never creates a host connection or opens an audio device. It emits JSON at `.build/native-transport-tests/results.json`. TSan is a separate run; an inability to initialize a sanitizer is not a test pass. This harness uses pinned native libraries for the current Mac architecture and macOS 14 deployment target. Mobile builds use separate iOS device and simulator slices prepared by `scripts/bootstrap-dependencies.sh --platform ios` and `--platform ios-simulator`, with platform audio-session/route adapters. The Mac harness does not execute those iOS output paths; tvOS builds remain future work. See [dependency preparation](dependencies.md#ios-native-libraries-and-openssl).
